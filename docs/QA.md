# 예상 질문과 답변 (한계를 솔직하게)

발표에서 나올 만한 질문을 **현재 상태 → 한계 → 다음 단계** 순으로 정리했습니다. 구현된 것과 설계만 한 것을 구분해 말하세요.

## 1. 차종 파라미터가 실제와 다르면 어떻게 되나요?

- **현재**: 차종 5종의 배터리 용량·최대 수용 출력·테이퍼링 최저 비율(kmin)은 시연용으로 임의로 정한 값입니다. 이름에 "(예시)"를 붙였고 화면에도 "실제 제원이 아닙니다"라고 표시합니다. 효율 η=0.92, 테이퍼 시작 80%도 PRD의 시연용 가정입니다.
- **한계**: 실제 충전 곡선은 온도·배터리 상태·충전기마다 다르고, 선형 테이퍼링은 단순화입니다. 오차 범위(0.92T~1.10T)는 근거 있는 통계가 아니라 표시 규칙입니다.
- **다음 단계**: 제조사 공개 사양으로 마스터를 채우고, 실측 충전 로그로 차종별 kmin·η를 회귀 보정합니다. 엔진은 γ(보정 계수)를 인자로 받도록 이미 열려 있습니다(기본 1.0).

## 2. 실제 충전기와 연동되나요?

- **현재**: 연동하지 않습니다. 시뮬레이터가 충전기 상태와 전력을 만들어 내고, 같은 상태를 DB에 미러링합니다. 시연은 "연동 없이도 전체 흐름이 재현된다"를 보여주는 것이 목적입니다.
- **한계**: OCPP·환경부 API는 붙어 있지 않아서 현재 부하(kW)는 시뮬레이션 값입니다.
- **다음 단계**: 계산 엔진(`app/engine`)은 DB·시계·FastAPI에 의존하지 않는 순수 함수라 입력 출처만 바꾸면 됩니다. 충전기 상태는 환경부 API, 실제 전력값은 OCPP MeterValues로 교체하는 어댑터 계층을 시뮬레이터 자리에 넣는 설계입니다(미구현).

## 3. 운전자가 입력한 SoC가 틀리면요?

- **현재**: 입력값을 그대로 쓰고, 예상 시간은 범위(예: 34~40분)로 표시합니다. 시뮬레이터에서는 충전 진행 SoC를 공식으로 계산하므로 입력 오차가 진행 중에 드러나지 않습니다.
- **한계**: PRD 3.6의 "실측과 20% 이상 어긋나면 γ를 세션 단위로 재추정하고 오차 범위를 넓힌다"는 **구현하지 않았습니다**. 충전기가 보고하는 SoC 대신 입력값을 믿습니다.
- **다음 단계**: 충전기 보고값(또는 경과시간 역산)을 s0로 다시 넣어 남은 시간을 갱신하고, 어긋남이 크면 γ를 재추정해 범위를 넓힙니다.

## 4. 노쇼와 방치는 어떻게 처리하나요?

- **노쇼**: 호출 후 5분 안에 진입하지 않으면 마지막 대기로 강등하고, 두 번째 노쇼는 대기를 종료합니다. 모바일 "시연 옵션"의 6분 진입으로 체험할 수 있습니다.
- **방치**: 충전이 끝났는데 차량이 5분 넘게 남아 있으면 관제 화면에 표시하고 **운전자 알림** 버튼으로 이동을 요청합니다. 방치 차량은 충전기를 실제로 점유하고 다음 대기자는 그동안 호출되지 않습니다.
- **한계**: 알림은 인앱 배너입니다(웹 푸시 미구현). 알림 후 "2분 뒤 이동"은 가상 운전자의 가정이고, 실제 이동을 강제하거나 과금으로 연결하지는 않습니다.

## 5. 우선순위가 공정한가요? 짧은 충전이 새치기하지 않나요?

- **현재**: 기본은 선착순입니다. 목표 SoC 80% 이하의 "빠른 충전"에만 `β·max(0, 30−T)` 가산점을 주고, 대기 30분을 넘긴 사람은 에이징으로 보호해 굶지 않게 했습니다. 호출된 차량의 순번은 잠깁니다.
- **한계**: β=0.5, 30분은 시연용 값이며 실제 충전소의 수요 분포로 튜닝하지 않았습니다.

## 6. 부하 제어가 운전자에게 불리하지 않나요?

- **현재**: 계약전력의 90%(λ)를 넘기지 않도록 새 차량은 여유 출력이 `P_eff`의 50% 이상이면 출력을 줄여 시작하고, 그보다 적으면 시작을 미룹니다. 어느 쪽이든 **사유와 새 예상 시각**을 폰에 띄우고 대기 취소 버튼을 항상 제공합니다.
- **한계**: 출력 제한은 해당 운전자의 충전 시간을 늘립니다. 제한된 출력은 이후 다른 차량이 끝나도 유지됩니다(시작 시점 기준 할당). 운전자 동의 절차나 요금 인센티브는 없습니다.

## 7. "피크 경감량"은 실제 효과를 보장하나요?

- **현재**: 같은 도착 순서·같은 충전기로 "제어 없음"과 "VoltQueue 적용"을 나란히 시뮬레이션해 비교합니다. 데모 시나리오(계약전력 300kW, 제어 한도 270kW) 전체를 돌리면 아래와 같습니다.

  | | 제어 없음 | VoltQueue 적용 |
  | --- | --- | --- |
  | 최대 부하 | 약 340kW | 270kW (피크 경감 약 70kW) |
  | 제어 한도 초과 시간 | 약 23분 | 0분 |
  | 평균 대기시간 | 약 32분 | 약 40분 |

- **트레이드오프**: 피크를 누르는 대가로 이 시나리오에서는 **평균 대기시간이 약 8분 늘어납니다.** 출력 제한과 시작 지연이 충전을 늦추기 때문입니다. "대기시간도 줄인다"고 말하면 안 되고, "계약전력 초과 없이 운영하는 대신 대기가 늘어나는 정도를 사유와 함께 투명하게 안내한다"고 설명하세요. (관제 화면의 평균 대기시간 카드가 보여주는 ▲▼는 전일 예시값과의 비교이지 제어 없음과의 비교가 아닙니다.)
- **한계**: 이 숫자는 임의로 만든 도착 시나리오의 결과입니다. 실제 수요 패턴, 운전자 행동(취소·이탈), 차종 믹스에 따라 달라지므로 효과 크기의 근거로 쓰면 안 되고 **동작 원리 증명**으로만 소개해야 합니다.
- **전일 대비 화살표**의 비교 대상(전일 KPI 7일치)도 시드의 예시값입니다. 오늘 값은 시뮬레이션 시작 이후의 누적이라 초반에는 "집계 중"으로 표시합니다.

## 8. 개인정보는요?

차량번호 등 식별정보를 수집하지 않습니다. 브라우저 localStorage의 익명 세션 ID만 사용합니다. 인증·권한은 없으며(관제 화면도 누구나 접근) 시연용입니다. 실서비스에서는 관제 화면 인증과 운영자 감사 로그가 필요합니다.

## 9. 얼마나 검증했나요?

- 계산 엔진: PRD 3.3의 검증 예시(36.7분)를 단위 테스트 기대값으로 고정했고, 테이퍼링 단조성 등 단위 테스트가 있습니다.
- 스케줄러·부하 제어·시뮬레이터·API: pytest 테스트가 있습니다(`make test`).
- 통합: `make e2e`가 PRD 7.3 시연을 폰(360px)·관제(1920×1080) 두 브라우저로 재현하고, 1440×900에서 화면이 한 번에 들어오는지와 콘솔 에러 0건까지 확인합니다.
- **한계**: 실제 충전기·실사용자 검증은 없습니다. E2E는 시뮬레이터 위에서 돕니다.

## 10. 규모를 키우면요?

- **현재**: 충전소 1곳, 충전기 3대, 시뮬레이션 상태는 서버 프로세스 메모리에 있습니다(재시작 시 초기화). 스냅샷은 클라이언트마다 0.5초 간격으로 푸시합니다.
- **한계**: 다수 충전소 히트맵(A-07)은 범위 밖입니다. 프로세스가 하나라 수평 확장 구조가 아닙니다.
- **다음 단계**: DB는 `DATABASE_URL`만 바꿔 PostgreSQL로 전환할 수 있게 해 두었습니다. 상태를 Redis 등으로 분리하고 충전소 단위로 런타임을 샤딩하는 것이 자연스러운 다음 단계입니다.

## 11. 한전KDN 관제 체계·DR/V2G와는 어떻게 이어지나요?

로드맵 항목이며 구현하지 않았습니다. 부하 한도 λ·P_contract를 고정값 대신 관제센터가 내려 주는 수요반응(DR) 신호로 바꾸면 같은 제어 로직이 "요청 시점에 충전 속도를 낮추는" 기능이 되고, V2G는 출력을 음수로 확장하는 문제입니다. 이 확장은 아직 설계 아이디어 수준입니다.
